- DemoExecutionBridge (this dir) runs only in engine-host when EXECUTION_MODE=DEMO_STRESS_TEST (default REAL_DISABLED), forwards only approved paper opens (READY + plan PLANNED + M4 APPROVED), validates DEMO mode + login/server whitelist, enforces DEMO_RISK_PROFILE, kill switch and one order per signal_id with write-ahead append-only log. Why: demo stress test needs real fills without any real-account path.
- Shadow Guard (src/core/execution/shadow/ShadowGuard.ts) sits between every approved intent and the demo bridge, and also wraps the demo gateway port so sendOrder is unreachable while shadow is active; shadow is ON unless SHADOW_MODE=OFF with EXECUTION_MODE=DEMO_STRESS_TEST, every attempt is an append-only shadow record, and duplicate/SL/TP/emergency-stop protections cannot be disabled. Why: a UI bug, wrong config, restart or reconnect must never reach a broker send.
- Phase 3.5: EXECUTION_MODE=SHADOW|DEMO is the single execution config (legacy DEMO_STRESS_TEST→DEMO, REAL_DISABLED/PAPER_ONLY/unset→SHADOW; SHADOW_MODE=ON forces shadow, OFF ignored). DemoExecutionLayer is wired in engine-host via asGatewayPort() between DemoExecutionBridge (risk validation) and shadowGatedGateway: fixed-order preflight (mode, duplicate, SL, TP, risk, symbol, account, position limit), append-only order lifecycle log with validated transitions, pure position reconciliation. Default SHADOW = analyze + journal only, no broker order. Why: one authoritative config, no ambiguous bypass.
- Phase 4A: risk_per_trade and execution limits live only in risk-policy.json (parsed by src/engine/risk/riskPolicy.ts, strict schema, env never overrides); broker lot comes only from buildFinalOrderPlan (M4, real broker balance/equity + contract spec), execution forwards it unchanged; PositionReconciler runs after every order and every 60s, and any mismatch blocks new orders (persisted across restart). Why: one auditable risk source, no silent drift between journal and broker.
- Phase 4A.1: balance/equity reach M4 only through an AccountStateProvider (src/engine/risk/accountStateProvider.ts: Simulated=PAPER, Broker=DEMO, REAL always null), and each demo trade is reconstructed under one tradeId from the append-only demo event log (tradeLifecycle.ts). Why: one account source and a journal that mirrors the broker.
- Phase 4A.2: ACCOUNT_MODE (PAPER|DEMO; REAL refused; EXECUTION_MODE=DEMO forces DEMO) selects the account base for paper M4 via MarketRuntime.setPaperAccountStateSource; in DEMO every M4 input (approval, lot, exposure, daily loss) uses the broker account state and fails closed when stale/unavailable; max_daily_loss lives in risk-policy.json. Why: approval and execution must use the same account.
- Phase 4B: demo evaluation dataset (src/core/execution/demo/evaluation.ts) is a pure read model over the append-only demo event log — trade snapshot (account/risk/market/technical/decision/execution/result + engine/strategy/journal versions), 9-stage lifecycle with NO_DECISION/NO_RISK/NO_RESULT violations, CSV export and descriptive stress counters at /v1/evaluation/*; broker closes come from bridge sync() deal history (tagged BROKER_DEAL_HISTORY), reconciliation is backup. Why: 100-trade demo must be auditable without any new decision path.
- Automation stage machine + 9-point checklist (src/core/enginehost/automationState.ts) and hybrid chart snapshots (chartSnapshot.ts: OHLC+SNR+event meta at PRE_ENTRY/ENTRY/CLOSE, SVG only at ENTRY/CLOSE) are observability-only projections; approval is only a session-level operator file engine-host/data/demo-arm.json (src/core/enginehost/demoArm.ts: armed + expiry + whitelisted login hash, kill switch wins, read-only, fail-closed) which also must hold before any approved open reaches the demo bridge (after Shadow Guard). Why: no per-trade approval, no web write path, shadow still blocks sends.
