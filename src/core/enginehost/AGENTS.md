- Persistent engine host (engine-host/ glue + src/core/enginehost) owns one MarketRuntime per symbol on the VPS via mountCanonicalRuntime, persists only the paper account (atomic snapshot) and journal (append-only JSONL) to VPS disk, re-bootstraps market/radar state from broker history, and exposes a GET-only engine-host-v1 API (+ SSE /v1/engine/events); the dashboard labels it ENGINE HOST VPS (LIVE) vs BROWSER SESSION (EPHEMERAL), never mixing the two. Why: engines must survive refresh/closed browser/VPS restart without an order path or cloud dependency.
- Engine state BOOTSTRAP until the radar has a real closed-history baseline (ATR percentile seeded from broker CLOSED M15); no default volatility/radar/confidence is ever shown. Why: no fabricated context.
- brokerClock.ts only observes drift (vps_receive − broker event_at) against a documented policy; it never rewrites candle timestamps. Why: broker time is the anchor, drift is surfaced not corrected.
- Phase 2.1 full attach: when the engine host is LIVE the dashboard is view-only (EngineHostStore: SSE SNAPSHOT_UPDATE → store → render; per-symbol EngineSymbolBundle incl. host-computed technical slice), the browser mounts no MarketRuntime, and every card reads one CockpitSource tagged ENGINE_HOST|BROWSER_SESSION; a mixed source renders STATE SOURCE MISMATCH. Why: single source of truth, no dual calculation, no polling blink.
- Proof of life: LivePaperLoop emits READY/BLOCKED/EXECUTION/EXIT observer events (stage-tagged) over the same merged broker-history evidence as the radar; EngineHost enriches them with radar intelligence (copy only) and serves GET /v1/engine/pipeline; the 5-min cloud capture appends them (plus demo lab events and RADAR candidates) to append-only engine_events and dispatches Telegram alerts logged in engine_notifications (PENDING when unconfigured, never failing capture). Why: every READY must end in a recorded OPEN or BLOCK reason, without the UI or AI touching execution.
- Telegram bot is the mobile face of the dashboard AI Assistant: alerts copy event facts verbatim and only the "Kenapa" text comes from the shared analystInstructions + buildLiveContext/memory context (bounded AI calls per capture run, facts-only fallback); the webhook answers only TELEGRAM_CHAT_ID and has no command that trades or changes config. VPS pipeline events go disk outbox → signed /api/public/agent/engine-events. Why: one AI, one source of truth, no event lost on restart.
- Execution readiness (src/core/enginehost/readiness.ts, GET /v1/engine/readiness and /v1/engine/:symbol/readiness) is a pure copy of outcomes LivePaperLoop already recorded plus demo status; missing data is UNKNOWN and old data STALE, never PASS. Why: show why demo orders do or do not happen without a second calculation.
- Engine host health carries build identity (buildInfo.ts: engine_version constant + commit/build_time from env or BUILD_INFO.json written by scripts/build-deploy-zip.sh; missing = null) and GET /v1/engine/version serves it. Why: know which code really runs on the VPS without trusting the dashboard.
- Execution status (src/core/enginehost/executionStatus.ts, GET /v1/engine/execution-status) is a read-only copy of demo arm, account, shadow, kill switch, reconciliation and recorded readiness; the dashboard EXE lamp (src/lib/exeLamp.ts) reads only it, and missing/stale (>30s) data is never green. Why: dashboard status must match the engine without a second calculation.
- Engine host SSE subscribers go only through SseHub (src/core/enginehost/sseHub.ts): idempotent cleanup on res/req/socket close, no write to closed sockets, congested clients skip frames and are dropped after a bounded wait/buffer; error listeners stay attached. Why: a dead or slow client must never grow host memory.
